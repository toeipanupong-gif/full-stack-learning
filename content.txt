เมื่อเรียนจบแล้ว เราจะเข้าใจภาพรวมตั้งแต่ “Request เข้ามา” จนถึง “Backend ทำงานเสร็จและตอบกลับ” รวมถึงเขียน Laravel เป็นระบบได้

หัวข้อนี้คือฐานของ Backend ทั้งหมด เพราะก่อนจะเรียน PHP/Laravel, Controller, Middleware, Database หรือ Queue เราต้องเห็นภาพก่อนว่า Request หนึ่งครั้ง “เดินทางผ่านอะไรบ้าง”

  "first_name": "John",
  "created_at": "..."
}

หรือ camelCase:
{
  "firstName": "John",
  "createdAt": "..."
}

ขอให้ทั้ง API มี Convention ชัด
50) Date / Time Contract
อย่าส่ง:
07/10/26

เพราะไม่รู้ Format ไหน
ควรใช้ Format มาตรฐาน เช่น ISO 8601 สำหรับ Timestamp
แนวคิด:
2026-10-07T10:30:00Z

หรือกำหนด Timezone ชัด
Date-only
ถ้าเป็นวันเกิด/วันที่นัดที่ไม่มีเวลา:
2026-10-07

อาจดีกว่า Timestamp
ต้องแยก Date กับ DateTime
51) null vs missing
สองอย่างต่างกัน
{
  "middle_name": null
}

หมายถึง Field มีอยู่แต่ไม่มีค่า
แต่:
{}

หมายถึง Field ไม่ถูกส่ง
โดยเฉพาะ PATCH สำคัญมาก
ตัวอย่าง PATCH
ถ้า:
{
  "phone": null
}

อาจหมายถึง:
ลบ phone

แต่ถ้าไม่มี phone เลย:
ไม่แก้ phone

Contract ต้องชัด
52) Boolean Naming
ควรใช้ชื่อเข้าใจง่าย:
is_active
has_permission
can_edit

มากกว่า:
status_flag
flag1

53) API Security Baseline
ทุก Endpoint ควรถาม:
ต้อง Login ไหม?
Permission อะไร?
Resource ownership?
Input validation?
Rate limit?
Sensitive output?

อย่าคิด Security ทีหลัง
54) IDOR
IDOR = Insecure Direct Object Reference
ตัวอย่าง:
GET /orders/100

User Login แล้วเปลี่ยนเป็น:
GET /orders/101

ถ้า Backendตอบ Order ของคนอื่น คือ Security Bug
ต้องตรวจ Ownership/Permission
55) Avoid Over-fetching Sensitive Data
Frontend ขอ User Profile
ไม่ควรตอบ:
{
  "id": 1,
  "name": "John",
  "password_hash": "...",
  "internal_note": "..."
}

แม้ Frontend “ไม่แสดง” ก็ไม่ควรส่ง
56) REST ไม่ใช่กฎศักดิ์สิทธิ์
บาง Action ไม่เข้ากับ CRUD สวย ๆ
เช่น:
Cancel order
Confirm payment
Transfer booking
Redeem coupon

สามารถใช้ Action Endpoint ที่สื่อความหมายได้
เช่น:
POST /orders/100/cancel
POST /payments/100/confirm

ดีกว่าฝืนทุกอย่างเป็น PATCH แบบอ่านไม่รู้เรื่อง
57) Command Endpoint
บาง Business Action คือ Command
เช่น:
POST /bookings/100/cancel

อ่านแล้วรู้ Intent ชัด
นี่โอเคถ้า Domain เหมาะ
58) REST กับ RPC ต่างกันคร่าว ๆ
REST เน้น:
Resource + HTTP semantics

RPC เน้น:
Action / Function call

เช่น:
/cancelBooking
/calculatePrice

ระบบจริงอาจผสมแนวคิดได้
ขอให้ Contract ชัดและ Consistent
59) API Evolution
API โตขึ้นควรหลีกเลี่ยง:
เพิ่ม field แบบมั่ว
rename field บ่อย
เปลี่ยน type เงียบ ๆ
เปลี่ยน semantics โดยไม่ version

เพราะ Client จะเปราะ
60) Deprecation
ถ้าจะเลิก API เก่า ควรมีช่วง Transition
เช่น:
v1 deprecated
v2 available

แจ้งทีม/Partner ให้ย้ายก่อนปิดจริง

ก่อนสร้าง Endpoint ถาม:
Resource คืออะไร?
Method อะไร?
Path อ่านรู้เรื่องไหม?
Request body มีอะไร?
Field ไหน trust ไม่ได้?
Validation อะไร?
Business rule อะไร?
Status code อะไร?
Response shape อะไร?
Error code อะไร?
ต้อง idempotent ไหม?
ต้อง transaction ไหม?
ต้อง pagination ไหม?
ต้อง version ไหม?

สรุป 3.2
REST API ที่ดีควรมี:
Resource-oriented endpoints
HTTP method ถูกความหมาย
Status code ถูกต้อง
Request/Response contract ชัด
Validation ชัด
Error shape consistent
Pagination/filter/sort ที่ควบคุมได้
Security/authorization
Idempotency สำหรับงานสำคัญ
Versioning/backward compatibility

และหลักที่สำคัญที่สุดคือ:
API ที่ดีไม่ได้วัดแค่ว่า Frontend เรียกได้ แต่ต้องมี Contract ที่ชัด, predictable และปลอดภัยพอให้หลาย Client ใช้ได้โดยไม่ต้องเดาพฤติกรรมของ Backend

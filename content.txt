6. Server / Linux / Deployment / DevOps
เมื่อเรียนจบแล้ว จะเข้าใจว่าเว็บจากเครื่อง Developer ถูกนำขึ้น Production อย่างไร ตั้งแต่โครงสร้าง Server, Linux, Process, Port, Network, Nginx, Reverse Proxy, Load Balancer, Node.js/PM2/systemd, PHP/PHP-FPM, Worker/Supervisor, Docker, Environment Variables, SSL/HTTPS, Domain/DNS, Logging, Monitoring, CI/CD, Deployment, Restart/Rollback ไปจนถึงการดูแลระบบให้รันต่อเนื่องและแก้ปัญหาเมื่อ Production มีปัญหาได้อย่างเป็นระบบ

6.1 Server Architecture & Production Request Flow แบบลงลึก
บทนี้คือจุดเริ่มต้นของฝั่ง Server / Linux / Deployment / DevOps เราจะมองภาพใหญ่ก่อนว่าเวลา User เปิดเว็บไซต์หนึ่งหน้า Request เดินทางผ่านอะไรบ้างใน Production จริง และแต่ละ Layer มีหน้าที่อะไร
Mental Model ใหญ่:
Browser
↓
DNS
↓
CDN / WAF
↓
Load Balancer
↓
Nginx / Reverse Proxy
↓
Application
├→ Next.js / Node.js
└→ PHP-FPM / Laravel
↓
Database / Redis / Queue / Object Storage

8) CDN ช่วยอะไร

10) WAF คืออะไร
WAF = Web Application Firewall
อยู่หน้า Application
ใช้ตรวจ Traffic เช่น:
malicious request
SQL injection pattern
bad bots
rate abuse

แต่ WAF ไม่แทน Secure Coding ใน Application
11) DDoS Protection
DDoS = Distributed Denial of Service
Attacker ส่ง Traffic จำนวนมากเพื่อทำให้ระบบรับไม่ไหว
CDN/Edge Provider ช่วยดูดซับ Traffic บางส่วนก่อนถึง Origin
12) หลัง CDN อาจมี Load Balancer
Load Balancer คือ Layer ที่กระจาย Request ไปหลาย Server
เช่น:
             ┌→ App 1
Client → LB ─┼→ App 2
             └→ App 3

13) ทำไมต้องมีหลาย App Servers
เพื่อ:
รองรับ traffic มากขึ้น
high availability
deploy ง่ายขึ้น
ลด single point of failure

ถ้า App 1 ตาย:
LB → App 2 / App 3

14) Load Balancing Algorithm
วิธีแบ่ง Request เช่น:
Round Robin
Least Connections
Weighted Round Robin
IP Hash

15) Round Robin
Request:
1 → Server A
2 → Server B
3 → Server C
4 → Server A

วนไป
16) Least Connections
ส่ง Request ไป Server ที่:
มี active connections น้อยที่สุด

เหมาะเมื่อ Request Duration แตกต่างกัน
17) Health Check
Load Balancer ต้องรู้ว่า Server ไหนยัง Healthy
เช่นเรียก:
GET /health

ถ้า Server ตอบผิด/ไม่ตอบ:
remove from rotation

18) Health Check ที่ดีไม่ควรหนัก
ไม่ควรทุก 5 วินาทีไป Query Report ใหญ่ ๆ
ควรเบา เช่น:
{
  "status": "ok"
}

19) Liveness และ Readiness
สองคำนี้สำคัญ
Liveness
ถามว่า:
process ยังมีชีวิตไหม?

Readiness
ถามว่า:
พร้อมรับ traffic จริงไหม?

20) ตัวอย่าง

แต่ DB Connection ใช้ไม่ได้

ควรถูกเอาออกจาก Load Balancer ชั่วคราว

สรุป 6.3
Security พื้นฐานของ Linux Server ไม่ได้หมายถึง “ตั้ง Password ยาก ๆ” อย่างเดียว แต่คือการกำหนด Identity, Privilege และ Network Exposure ให้ถูกต้อง:
Human User
→ individual SSH key + limited sudo

Service User
→ only permissions needed by app

Files
→ correct owner/group/mode

Network
→ expose only required ports

Secrets
→ readable only by required identities

หลักสำคัญที่สุดคือ:
อย่ารันทุกอย่างเป็น root และอย่าแก้ Permission ด้วย 777; ให้รู้ก่อนว่า Process รันเป็น User ไหน แล้วให้สิทธิ์เฉพาะ File/Directory ที่มันจำเป็นต้องใช้

และสำหรับ SSH/Firewall:
ทุกครั้งที่แก้ Remote Access ให้มี Recovery Path — เก็บ Session เดิมไว้, Validate Config และทดสอบ Connection ใหม่ก่อนปิดทางเข้าเดิม

202) Production Rule

204) และอีกข้อ

สรุป 6.4

6.5 Linux Networking, Ports, DNS & Connectivity Troubleshooting แบบลงลึก

เป็น Address ที่ Routable บน Internet

ไม่ได้

205) อีก Mental Model
Nginx ทำหน้าที่หลัก 4 เรื่อง:
1. Listen
2. Match
3. Serve or Forward
4. Observe/Protect

คือ:
listen port/domain
↓
match location
↓
serve file / proxy
↓
logs, TLS, limits, headers

สรุป 6.6
Nginx คือ Gateway ฝั่ง Web ที่รับ Request ก่อน Application และสามารถทำ:
HTTPS / TLS
Reverse Proxy
Static Files
Virtual Hosts
Load Balancing
Headers
Compression
Rate/Body Limits
Logging

สิ่งที่ต้องจำให้แม่นคือ:
server
→ domain / port

location
→ path routing

proxy_pass
→ HTTP backend เช่น Node

fastcgi_pass
→ PHP-FPM

root / alias
→ static filesystem mapping

และเวลาเจอ Error:
404
→ routing/file/app route

403
→ permission/deny/directory

502
→ upstream ติดต่อไม่ได้หรือ response ผิด

504
→ upstream ตอบไม่ทัน

413
→ body ใหญ่เกิน

หลักสำคัญที่สุดคือ:
ก่อน Reload Nginx ทุกครั้งให้ใช้ nginx -t และเวลา Error ให้แยกว่า Request พังที่ Nginx เอง หรือพังที่ Upstream Application

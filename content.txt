7. Security & System Design
เมื่อเรียนจบแล้ว จะเข้าใจการออกแบบระบบให้ ปลอดภัย รองรับการ Scale และทนต่อความผิดพลาด ตั้งแต่ Authentication, Authorization, XSS, CSRF, SQL Injection, Secrets ไปจนถึง Load Balancer, Cache, Database, Queue, High Availability และ Distributed Systems.


7.1 Security Fundamentals, Threat Modeling & Attack Surface แบบลงลึก
บทนี้จะปูพื้นฐานก่อนเข้าเรื่อง Authentication, Authorization, XSS, CSRF, SQL Injection, CORS และ OWASP โดยเริ่มจากการคิดว่า อะไรคือสิ่งที่เราต้องป้องกัน, ใครอาจโจมตี, โจมตีผ่านทางไหน และผลกระทบคืออะไร

1) Security ไม่ใช่แค่ “กัน Hacker”
Security คือการรักษา:
Confidentiality
Integrity
Availability

เรียกว่า CIA Triad
2) Confidentiality
หมายถึงข้อมูลต้องถูกเห็นเฉพาะคนที่มีสิทธิ์

เช่น:
password
access token
customer data
payment data
internal API key

ถ้าคนที่ไม่ควรเห็นเข้าถึงได้:
Confidentiality broken

3) Integrity
หมายถึงข้อมูลต้องไม่ถูกแก้ไขโดยไม่ได้รับอนุญาต

เช่น:
ราคา 1,000
ถูกแก้เป็น 1

หรือ:
booking status
waiting_for_payment
→ booking_successful

โดย Userแก้เอง

นี่คือ Integrity Problem
4) Availability
ระบบต้องพร้อมใช้งาน

เช่น:
DDoS
resource exhaustion
database outage

ถ้า Userเข้าไม่ได้:
Availability broken

5) Security ไม่ได้แปลว่าต้องป้องกันทุกอย่าง 100%
ไม่มีระบบปลอดภัย 100%

เราต้องบริหาร:
Risk

6) Risk คืออะไร
Conceptง่าย ๆ:
Risk ≈ Likelihood × Impact

คือ:
โอกาสเกิด
×
ความเสียหายถ้าเกิด

7) Example
หน้า Adminถูกโจมตียากมาก

Likelihoodต่ำ

แต่ถ้าเข้าได้สามารถลบ Userทั้งหมด

Impactสูง

ดังนั้น Riskยังสูงได้
8) Threat คืออะไร

9) Vulnerability
Vulnerability = ช่องโหว่

เช่น:

= Threat

SQL Injection bug
= Vulnerability

7.2 Authentication vs Authorization & Identity Fundamentals แบบลงลึก
บทนี้จะวางพื้นฐานเรื่อง Identity, Authentication และ Authorization ซึ่งเป็นหัวใจของระบบ Login ทั้งหมด ก่อนจะไป Session, JWT, OAuth 2.0, OpenID Connect และ MFA ในบทถัด ๆ ไป

↓

↓
Authorization
↓

Who are you?
↓

7.3 Password Security, Session Management, Cookies & MFA แบบลงลึก
บทนี้จะลงลึกว่า หลังจากเราเข้าใจ Authentication แล้ว ระบบควร เก็บ Password อย่างไร, Session ทำงานอย่างไร, Cookie ต้องตั้งค่าอะไร, Session ถูกขโมยได้อย่างไร และ MFA ช่วยเพิ่มความปลอดภัยตรงไหน

Mental Model:
Password
↓
Authenticate
↓
Create Session
↓
Store Session ID in Secure Cookie
↓
Browser sends Cookie each request
↓
Server validates Session
↓
Authorize Action

1) Password ไม่ควรถูกเก็บแบบ Plaintext
ไม่ควรเก็บ:
email                password
user@example.com     MyPassword123

เพราะถ้า Database หลุด:
ทุก Password ถูกเปิดเผยทันที

และ User หลายคนใช้ Password ซ้ำกับบริการอื่นด้วย
2) Password ต้อง Hash
ควรเก็บ:
password
↓
password hashing algorithm
↓
password hash

เช่น:
$argon2id$...

Serverไม่จำเป็นต้องรู้ Passwordจริงอีก
3) Hash คืออะไร
Hash คือ Function แบบ:
input
↓
hash function
↓
fixed-length output

โดยออกแบบให้ย้อนกลับไม่ได้ง่าย

เช่น:
hello
→ hash

แต่ Password Hashingมี Requirementมากกว่า Hashทั่วไป
4) ทำไม SHA-256 อย่างเดียวไม่เหมาะกับ Password
SHA-256ถูกออกแบบให้:
เร็ว

แต่สำหรับ Password:
เร็ว = ไม่ดี

เพราะ Attackerสามารถลอง Passwordจำนวนมหาศาลได้เร็วมาก
5) Password Hashingควรตั้งใจให้ช้า
เพื่อให้:
User login
→ delayเล็กน้อย

Attacker brute-force
→ แพงมาก

นี่คือ Desired Property
6) Algorithms ที่นิยม
เช่น:
Argon2id
bcrypt
scrypt
PBKDF2

ในระบบใหม่ Argon2idเป็นตัวเลือกที่แข็งแรงมากเมื่อ Frameworkรองรับ
7) Argon2id
Argon2idเป็น Password Hashing Algorithmที่ปรับได้ทั้ง:
memory cost
time cost
parallelism

ทำให้โจมตีด้วย GPU/Hardwareจำนวนมากแพงขึ้น
8) bcrypt
ยังใช้แพร่หลายมาก

มี:
cost factor

ยิ่งสูงยิ่งใช้เวลาคำนวณมาก

แต่ต้อง Balanceกับ Production Login Capacity
9) Cost Factor
สมมติ Hashหนึ่งครั้งใช้:
100ms

Login 10 ครั้งไม่ใช่ปัญหา

แต่ Attackerลอง:
1,000,000 passwords

จะเสียเวลามาก
10) แต่ Costสูงเกินไปก็กลายเป็น DoSได้
ถ้า Hashใช้:
5 seconds

ต่อ Login

Attackerยิง Loginจำนวนมาก:
CPU saturation

ดังนั้นต้อง Benchmarkบน Production-like Hardware
11) Salt คืออะไร
Saltคือ Random Valueที่สร้างต่อ Password

เช่น:
password = hello123
salt = randomXYZ

นำไป Hashร่วมกัน
12) ทำไมต้อง Salt
ถ้า User A และ Bใช้ Passwordเดียวกัน:
hello123

ถ้าไม่มี Salt:
same password
→ same hash

Attackerเห็นทันทีว่าใช้ Passwordเหมือนกัน
13) มี Salt แล้ว
User A salt=A
User B salt=B

แม้ Passwordเดียวกัน:
hashต่างกัน

14) Salt ไม่ต้องเป็น Secret
Saltสามารถเก็บข้าง Password Hashได้

Modern Password Hash Librariesมักจัดการ Saltให้อัตโนมัติ
15) อย่าสร้าง Password Hashเองถ้าไม่จำเป็น
ใช้ Library/Frameworkที่ผ่านการตรวจสอบแล้ว

cost

↓

↓

↓

7.4 JWT, Access Token, Refresh Token & Token Security แบบลงลึก
บทนี้จะอธิบายเรื่อง Token-based Authentication โดยเฉพาะ JWT, Access Token และ Refresh Token ว่าจริง ๆ แล้วทำงานอย่างไร, ต่างจาก Session แบบไหน, ใช้เมื่อไร, มีข้อดีข้อเสียอะไร และต้องป้องกัน Token Theft/Replay/Revocation อย่างไร

225) Mental Model: OAuth 2.0
OAuth คือการให้สิทธิ์ Client เข้าถึง Resource โดยไม่มอบ Password ของ User ให้ Client

226) Mental Model: OpenID Connect
OIDC เพิ่ม Identity ลงบน OAuth เพื่อให้ Clientรู้ว่า Userที่ authenticate สำเร็จคือใคร

227) Mental Model: Authorization Code
Code เป็น Credentialชั่วคราวแบบ one-time ที่ต้องนำไป exchange เพื่อรับ Token ไม่ใช่ Tokenสำหรับเรียก API

228) Mental Model: PKCE
แม้ Authorization Codeถูกขโมย ผู้โจมตียัง exchange ไม่ได้ถ้าไม่มี Code Verifier

229) Mental Model: state
Callbackนี้ต้องเป็นคำตอบของ Login Flowที่เราเริ่มเอง ไม่ใช่ Flowที่ Attackerสร้างมาให้

230) Mental Model: nonce
ID Tokenนี้ต้องสัมพันธ์กับ Authentication Requestที่เราเป็นคนเริ่ม

231) Mental Model: Social Login
Provider
→ proves external identity

Our App
→ maps identity to local user

Our Authorization
→ decides what local user can do
